  • UPPERCASE = SQL keywords (the language), lowercase = your table / column names. MySQL is case-insensitive for keywords; many servers are case-sensitive for table names on Linux — so stay lowercase.

SQL & Databases 101

Before writing a single query, understand what you're talking to. This chapter builds the mental model — tables, the SQL language families, and the MySQL server/client split — using the very first commands from Lecture 1.

What is a relational database, really?

A database is a program whose entire job is to store data safely and answer questions about it fast. A relational database (RDBMS) stores that data in tables — grids of rows (one entity, e.g. one person) and columns (one attribute, e.g. their age). Think “super-powered spreadsheet” with three superpowers a spreadsheet lacks:

  • Types & constraints — a column declares what it accepts (INT, dates, max lengths), so bad data can be rejected at the door.
  • Relationships — tables can reference each other (“this order belongs to that person”), and the engine enforces those references.
  • Set-based querying — you describe which rows you want in one statement; the engine figures out how to fetch millions of them. You never loop.

SQL (Structured Query Language) is how you talk to it. It's declarative: you state the result, not the procedure.

The server / client split

When you ran the notebooks, two programs were involved. The MySQL Server is a background service that owns the data files and does all the real work. Everything else — the MySQL Shell, VS Code's notebook extension, Workbench, your future apps — is just a client that sends SQL text over a connection and draws the results. This is why the same queries work identically in every tool.

🖥️ Your SQL (notebook cell) → 🔌 client (MySQL Shell / VS Code) → 🗄️ MySQL Server (:3306) → 💾 data on disk

Creating Databases & Tables

A table is a contract: “every row that enters will have these columns, of these types, obeying these rules.” This chapter teaches you to write that contract — data types, constraints, and the two production-grade schemas from Lectures 1 and 5.

CREATE — from nothing to a working table

SQL📓 Lecture 1
CREATE TABLE maqbool_info (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    name        VARCHAR(50) NOT NULL,
    age         INT NOT NULL,
    gender      VARCHAR(50) NOT NULL,
    is_student  BOOLEAN DEFAULT TRUE
);

SHOW TABLES;      -- confirm it exists
DESC maqbool_info; -- inspect the contract

Five lines, five decisions: each column gets a name, a type, and zero or more constraints. Here is what MySQL recorded — the exact DESC output from the notebook:

🧠 Masterclass insight — reading DESC like a pro

Null = may this column be empty? Key = PRI primary key, UNI unique, MUL indexed. Default = value used when you don't supply one. Extra = engine-side behavior like auto_increment. Also notice: BOOLEAN was stored as tinyint(1) — in MySQL, BOOL is an alias; TRUE/FALSE are just 1 and 0 wearing a costume.

⚠️ Watch out

Money is DECIMAL, full stop. FLOAT/DOUBLE are binary approximations: 0.1 + 0.2 ≠ 0.3. An e-commerce total that drifts by a paisa per order becomes an accounting nightmare. Also: TIMESTAMP ends in 2038 — fine for created_at, wrong for birthdates or “contract expires 2040”.

A production-grade schema, annotated

Lecture 5 built this orders table — every type decision above, in one place:

SQL📓 Lecture 5
CREATE TABLE orders (
    id              INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id         INT UNSIGNED NOT NULL,               -- who ordered (FK added in Ch 11)
    order_number    VARCHAR(20)  NOT NULL UNIQUE,        -- business ID, no duplicates
    status          ENUM('pending','confirmed','processing',
                         'shipped','delivered','cancelled','refunded')
                         NOT NULL DEFAULT 'pending',     -- closed set + safe default
    total_amount    DECIMAL(10,2) NOT NULL,              -- exact money: up to 99,999,999.99
    item_count      TINYINT UNSIGNED NOT NULL DEFAULT 1, -- small non-negative counter
    payment_method  ENUM('credit_card','debit_card','upi',
                         'net_banking','cod','wallet') NOT NULL,
    created_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                              ON UPDATE CURRENT_TIMESTAMP  -- auto "last modified"
);
🧠 Masterclass insight — constraints are the database defending itself

Every constraint is a promise the engine enforces forever, no matter which buggy app, script, or tired human talks to it. NOT NULL blocks “forgetting”, DEFAULT supplies the sane value, UNIQUE blocks duplicates, ENUM blocks typo-states like 'Delivered '. Applications come and go — the contract stays. Design constraints first, not “later”.

💡 Pro tip — the audit-columns pattern

Almost every serious table carries created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP and updated_at … ON UPDATE CURRENT_TIMESTAMP. The database fills both automatically — zero application code — and you get free forensics (“when did this row change?”). Lecture 4 added exactly these to maqbool_info.

Modifying & Destroying

Schemas evolve and data gets removed. This chapter covers ALTER TABLE, then draws the line every developer must never blur: DELETE vs TRUNCATE vs DROP — using two painful (and instructive) moments from Lecture 1.

ALTER TABLE — reshaping a live table

You never have to get a schema right the first time. Lecture 1 grew maqbool_info twice:

SQL📓 Lectures 1 & 4
-- add a brand-new column (existing rows get NULL / the default)
ALTER TABLE maqbool_info ADD phone_number VARCHAR(20);

-- change a column's definition: age may now be empty, defaults to NULL
ALTER TABLE maqbool_info MODIFY COLUMN age INT DEFAULT NULL;

-- add the audit timestamps (Ch 2 pattern)
ALTER TABLE maqbool_info ADD COLUMN createdAt TIMESTAMP DEFAULT CURRENT_TIMESTAMP;

-- rename a column (MySQL 8):
ALTER TABLE maqbool_info RENAME COLUMN createdAt TO created_at;

-- remove a column entirely (data gone with it):
ALTER TABLE maqbool_info DROP COLUMN phone_number;

📓 From your notebook

Lecture 4 ran ALTER TABLE maqbool_info MODIFY COLUMN updatedAT TIMESTAMP … before updatedAT existed — MySQL answers with Error 1054: Unknown column. The lesson stuck: MODIFY edits what is; ADD creates what isn't. If a column is missing, you need ADD.

📓 From your notebook — the DELETE that ate too much

Lecture 1 ran DELETE FROM maqbool_info WHERE name='Maqbool'; and every Maqbool row vanished at once — the table held several rows with the same name, because names are not unique. That's the moment you learn: filter by the primary key (WHERE id = 3) when deleting one thing, and make business identifiers UNIQUE (Ch 2) when duplicates are meaningless.

💡 Pro tip — the safe-DELETE ritual

Before any destructive statement, run the identical WHERE as a SELECT first:

-- step 1: preview exactly what will die
SELECT * FROM maqbool_info WHERE id = 3;
-- step 2: only then pull the trigger
DELETE FROM maqbool_info WHERE id = 3;

And remember the next chapter's tool: wrap risky changes in a transaction so ROLLBACK can save you (Ch 13).

Inserting Data — INSERT Done Right

Rows enter a table only through INSERT. Simple — until a phone number loses its +, or a value lands in the wrong column. This chapter covers every insertion pattern from Lectures 1, 2 and 7, plus the quoting rule that would have saved all of it.

The anatomy of an INSERT

SQL📓 Lecture 1
INSERT INTO maqbool_info (name, age, gender, is_student, phone_number)
VALUES ('Arbaz', 23, 'male', FALSE, '+91345376898932');

-- several rows in one statement — one round-trip, one statement to read:
INSERT INTO maqbool_info (name, age, gender, is_student, phone_number)
VALUES ('Arbaz',   23, 'male', FALSE, '+91345376898932'),
       ('Maqbool', 20, 'male', FALSE, '+9142354543');
  • The column list is the map. It pairs each value with its destination column, so order mistakes are impossible and new columns (like created_at) don't silently shift your values. Omit it and you must supply every column in exact table order — fragile. Always write the list.
  • Skipped columns get their DEFAULT — id auto-increments, is_student would have become 1 if omitted.
  • Multi-row VALUES scale to hundreds of rows (Lecture 2 seeded ~127 people in exactly one such statement).
📓 From your notebook — the vanishing “+”

Lecture 1 inserted the phone as +91345376898932 — unquoted. MySQL read it as arithmetic on a number and stored 91345376898932: the + vanished. A phone written as 09876543210 would have lost its leading 0 the same way. Rule: if it isn't math, it isn't a number. Phone numbers, pin codes with leading zeros, ID card numbers — always strings.

🧠 Masterclass insight — what NULL and DEFAULT really do

Inside VALUES, the keywords NULL and DEFAULT are first-class values: VALUES ('Zara', 22, 'female', DEFAULT, NULL) explicitly says “use the column's default” and “store emptiness”. Lecture 7's seed rows did exactly this — inserting explicit IDs with NOW() timestamps:

INSERT INTO maqbool_info (id, name, age, gender, is_student, phone_number, created_at, updated_at)
VALUES (128, 'Arbaz Khan', 25, 'male', 1, '9876543210', NOW(), NOW()),
       (130, 'Zara Patel', 22, 'female', 1, NULL, NOW(), NOW());   -- phone = no phone

⚠️ Watch out

Three classic insert errors: column count mismatch (Error 1136 — values ≠ listed columns), duplicate key (Error 1062 — a UNIQUE/PRIMARY value already taken), and out-of-range / wrong ENUM value (Error 1265) — strict mode rejects instead of silently mangling. Read the error; it names the culprit.

Reading Data — SELECT & the Logical Order

You'll write more SELECTs than everything else combined. Beyond the basics from Lecture 2, this chapter hands you the single most useful model in all of SQL: the logical processing order — the lens that later explains GROUP BY, HAVING, aliases and LIMIT in one shot.

Projection: choosing columns

SQL📓 Lecture 2
SELECT * FROM maqbool_info;              -- every column (fine for exploring)
SELECT id, name, age FROM maqbool_info;  -- only what you need
SELECT gender, phone_number FROM maqbool_info;

-- aliases rename output columns; expressions compute on the fly:
SELECT name AS user_name, age AS user_age, age + 5 AS age_in_5_years
FROM maqbool_info;

SELECT DISTINCT gender FROM maqbool_info;          -- unique values only
SELECT DISTINCT age, gender FROM maqbool_info;     -- unique combinations
💡 Pro tip

SELECT * is for humans exploring, not for applications. Selecting 30 columns to use 3 wastes network, memory, and — once indexes exist (Ch 16) — can even disable the fastest read path. Name your columns; the query also becomes self-documenting.

The master key: logical processing order

SQL is written top-to-bottom but executed in a different order. Burn this sequence in — every “why can't I do X?” question for the rest of this guide is answered by it:

1FROM / JOINgather the source rows
↓
2WHEREfilter individual rows
↓
3GROUP BYcollapse rows into groups
↓
4HAVINGfilter whole groups
↓
5SELECTcompute output columns & aliases
↓
6ORDER BYsort the final rows
↓
7LIMIT / OFFSETkeep a window of them
🧠 Masterclass insight — why the order explains everything

You can't use a SELECT alias inside WHERE — step 2 runs before step 5, so the alias doesn't exist yet. You can use it in ORDER BY — step 6 runs after. WHERE sees raw rows (before grouping); HAVING sees groups (after). This one diagram is why Ch 9's “HAVING vs WHERE” and Ch 7's “ORDER BY the alias” both work. When a query confuses you, number its clauses 1–7 and re-read it in execution order.

Aliasing — for columns and for tables

SQLpattern · everywhere ahead
SELECT m.name AS person,
       m.age  AS years_old
FROM maqbool_info AS m;      -- table alias: from Ch 12 onward you'll write m, o, ad constantly
⚠️ Watch out

Aliases are strings to the outside world: SELECT age + 5 AS "age in 5y" needs quotes because of spaces. And in ORDER BY, a bare number (ORDER BY 2) sorts by the 2nd output column — legal, but don't: one added column silently reorders your results.

Filtering — WHERE, IN, LIKE & NULL Logic

WHERE is where analysis begins: from “all rows” to “exactly the rows that matter”. Lectures 2 and 3 hammered these operators against 127 people — this chapter systematizes them and confronts the strangest citizen of SQL: NULL.

Comparison operators

SQL📓 Lecture 2
SELECT * FROM maqbool_info WHERE id = 1;
SELECT * FROM maqbool_info WHERE age >= 21;
SELECT * FROM maqbool_info WHERE gender <> 'male';   -- <> or != — same thing
SELECT * FROM maqbool_info WHERE age BETWEEN 18 AND 25;  -- inclusive both ends

Combining conditions — AND, OR, NOT

SQL📓 Lecture 3
SELECT * FROM maqbool_info WHERE name LIKE 'Arbaz%' AND gender = 'male';
SELECT * FROM maqbool_info WHERE name LIKE 'Arbaz%' AND is_student = TRUE;
SELECT * FROM maqbool_info WHERE name NOT LIKE 'Arbaz%' AND age = 22
ORDER BY id ASC;
🧠 Masterclass insight — AND binds tighter than OR

WHERE name = 'Arbaz' OR gender = 'female' AND age = 22 does not mean “(name or gender) and age”. AND wins: it parses as name='Arbaz' OR (gender='female' AND age=22) — every male Arbaz of any age sneaks in. Parenthesize whenever AND and OR mix. Reading your own query six months later counts too.

IN — the readable OR

SQL📓 Lecture 2
SELECT * FROM maqbool_info WHERE name IN ('Arbaz', 'Arbaz Khan', 'Esha Solanki');
SELECT * FROM maqbool_info WHERE id IN (1, 23, 3, 4, 53);

SELECT * FROM maqbool_info
WHERE age NOT IN (21, 31, 44)
  AND gender = 'female';

IN is equivalent to a chain of = joined by OR — shorter, clearer, and (unlike that chain) it can also take a subquery, which is exactly where Chapter 10 takes it.

NULL — the value that isn't a value

After Lecture 4 made age nullable and set some rows to NULL, one rule became unavoidable:

SQL📓 Lecture 4
UPDATE maqbool_info SET age = NULL WHERE age = 0;   -- unknown age, honestly stored

SELECT COUNT(*) FROM maqbool_info;                  -- counts everyone
SELECT COUNT(age) FROM maqbool_info;                -- counts only known ages!
SELECT * FROM maqbool_info WHERE age IS NULL;       -- find the unknowns
SELECT * FROM maqbool_info WHERE age IS NOT NULL;
🧠 Masterclass insight — three-valued logic

NULL means “unknown”, not zero and not empty string. Any comparison with an unknown yields unknown — so WHERE age = NULL matches nothing, ever, and WHERE age <> 21 also silently skips NULL-age rows (unknown isn't ≠ 21; it's unknown). The language has three truth values — TRUE, FALSE, UNKNOWN — and only TRUE survives a WHERE. Hence: IS NULL / IS NOT NULL are not style choices; they're the only correct tools. Ch 8 shows aggregates joining the conspiracy by ignoring NULLs too.

Sorting & Paging — ORDER BY, LIMIT, OFFSET

Tables have no natural order — a “sorted table” only exists at query time. Lecture 3 practiced ORDER BY, Lecture 2 paged through 127 people with LIMIT … OFFSET …. Here's the full mental model, plus the trap that makes unordered LIMIT a lottery.

ORDER BY — imposing order at read time

SQL📓 Lecture 3
SELECT * FROM maqbool_info WHERE name LIKE 'Arbaz%' AND age = 22
ORDER BY id DESC LIMIT 10 OFFSET 0;          -- newest first

SELECT * FROM maqbool_info WHERE name NOT LIKE 'Arbaz%' AND age = 22
ORDER BY name ASC;                            -- alphabetical

-- multiple keys: sort by name, break ties by id (descending):
SELECT name, age FROM maqbool_info ORDER BY name ASC, id DESC;
  • ASC is the default (A→Z, 0→9, old→new); DESC flips it.
  • Multiple keys = tie-breakers: rows equal on the first key are ordered by the second.
  • You may sort by output aliases (ORDER BY user_name) or even by column position (ORDER BY 2) — prefer names; positions break silently.
🧠 Masterclass insight — where does the sort happen?

By the logical order, ORDER BY is step 6: it sorts the finished result set, after filtering and column selection. That's why you can sort by expressions and aliases that exist nowhere in the table. The cost: for big unsorted data MySQL must materialize and sort rows (“filesort” in EXPLAIN — Ch 16). An index on the sorted column can hand the engine pre-sorted data — one of the quiet ways indexes pay rent.

LIMIT & OFFSET — windows on a result set

SQL📓 Lecture 2 · paging through 127 people
SELECT * FROM maqbool_info ORDER BY id LIMIT 10 OFFSET 0;    -- page 1
SELECT * FROM maqbool_info ORDER BY id LIMIT 10 OFFSET 10;   -- page 2
SELECT * FROM maqbool_info ORDER BY id LIMIT 10 OFFSET 20;   -- page 3
SELECT * FROM maqbool_info ORDER BY id LIMIT 10 OFFSET 30;   -- page 4

-- MySQL shorthand: LIMIT offset, count  (note the swapped order!)
SELECT * FROM maqbool_info ORDER BY id LIMIT 20, 10;         -- = OFFSET 20 LIMIT 10
💡 Pro tip — the pagination formula

For page p with n rows per page: LIMIT n OFFSET (p-1)*n. Page 5 of 10-per-page → LIMIT 10 OFFSET 40. Always pair the same ORDER BY with every page request — that's what makes “page 2” a place rather than a dice roll.

⚠️ Watch out — LIMIT without ORDER BY is a lottery

SELECT * FROM maqbool_info LIMIT 10 returns “some 10 rows” — whichever the storage engine touches first, which can change with indexes, cache state, and updates. Two runs can disagree. Lecture 2's paged queries were only stable because id ordered them (explicitly or via the table's clustered index). Rule: LIMIT in any serious query ⇒ ORDER BY a unique key.

Top-N — the everyday pattern

SQLpattern · reused in Project 1
-- the 5 oldest people:
SELECT id, name, age
FROM maqbool_info
ORDER BY age DESC
LIMIT 5;
🧠 Masterclass insight — deep pages get expensive

OFFSET 100000 LIMIT 10 makes MySQL produce, sort, and throw away 100,010 rows to show 10. Pages past the first few get slower linearly. Real apps switch to keyset pagination — “continue after the last id I saw”: WHERE id > 100000 ORDER BY id LIMIT 10 — constant speed at any depth, at the cost of “jump to page 47” links. File this away for your first dashboard.

Aggregates — COUNT, SUM, MIN, MAX, AVG

An aggregate collapses many rows into one answer. Lecture 4 ran a beautiful experiment: make age nullable, then watch COUNT(*) and COUNT(age) disagree. That gap is this chapter's core lesson — aggregates have opinions about NULL, and you must know them.

The five workhorses

SQL📓 Lecture 4
SELECT COUNT(*)             AS total_rows,     -- every row
       COUNT(age)           AS known_ages,     -- rows where age IS NOT NULL
       COUNT(DISTINCT age)  AS different_ages, -- unique non-NULL ages
       SUM(age)             AS total_age,      -- sum of non-NULL ages
       MIN(age)             AS youngest,
       MAX(age)             AS oldest,
       AVG(age)             AS average_age
FROM maqbool_info;
FunctionReturnsNULL behavior
COUNT(*)number of rowscounts everything, NULLs included
COUNT(col)rows where col is knownskips NULLs
COUNT(DISTINCT col)unique known valuesskips NULLs
SUM(col)totalskips NULLs — all-NULL input → returns NULL, not 0
MIN / MAX(col)extremesskips NULLs; empty input → NULL
AVG(col)meanskips NULLs — and that changes the denominator!
🧠 Masterclass insight — AVG's hidden division

AVG(age) = SUM(age) / COUNT(age) — divided by known ages only. If 100 people have ages and 27 don't, the average is over 100, not 127. Sometimes that's exactly right (“average of known ages”), sometimes it's a lie (“average age of our users” should perhaps count unknowns as excluded, or be reported with the known-count next to it). That's why the lecture selected COUNT(*) and COUNT(age) side by side: always publish your denominator.

📓 From your notebook — COUNT of an expression

Lecture 4 tried SELECT COUNT(age > 22) FROM maqbool_info; expecting “people over 22”. It returned something suspicious: COUNT counts non-NULLs, and age > 22 evaluates to 1 or 0 — never NULL — for every known age. So it counted nearly everyone. The correct form (and a pattern you'll reuse constantly in Ch 15):

SELECT COUNT(*) FROM maqbool_info WHERE age > 22;                  -- simplest
SELECT SUM(age > 22) FROM maqbool_info;                            -- counts the 1s
SELECT COUNT(CASE WHEN age > 22 THEN 1 END) FROM maqbool_info;     -- NULL when false → skipped

Aggregates are just numbers — do math with them

SQL📓 Lecture 4
SELECT SUM(age) + COUNT(gender) FROM maqbool_info;   -- fine: each side collapses to a scalar
SELECT SUM(age) / COUNT(*)    AS avg_incl_nulls     -- manual AVG that divides by ALL rows
FROM maqbool_info;

Because every aggregate returns a single value, expressions over aggregates behave like ordinary arithmetic — the seed of conditional aggregation (Ch 15) and per-group math (Ch 9).

💡 Pro tip — alias everything you aggregate

Unaliased aggregates arrive with ugly headers like COUNT(Distinct age). The lecture quickly adopted AS total_age, AS minimum_age. Aliases make results readable and let ORDER BY / wrappers reference the number later. One-word habit, permanent payoff.

Grouping — GROUP BY, HAVING & Duplicate Hunters

One aggregate over a whole table answers one question. GROUP BY asks the question once per category — per name, per status, per pincode. And HAVING filters those answers. Lecture 4's duplicate hunt is the classic training ground.

GROUP BY — one row per group

SQL📓 Lecture 5
SELECT age         AS age,
       COUNT(age)  AS age_count
FROM maqbool_info
GROUP BY age
HAVING COUNT(age) > 1        -- keep only ages shared by 2+ people
ORDER BY age ASC;

Mentally, the engine: sorts/buckets rows by age, then runs COUNT inside each bucket. One bucket → one output row. That's the whole trick — everything else is which bucket key and which filter.

🧠 Masterclass insight — only_full_group_by, and ANY_VALUE

Try SELECT name, COUNT(*) FROM maqbool_info GROUP BY age; and MySQL 8 (with only_full_group_by on, the default) refuses: name isn't grouped or aggregated — which name would the age-bucket even show? Every selected column must be either in GROUP BY or inside an aggregate. Lecture 4 hit this wall and escaped with the sanctioned shrug:

SELECT ANY_VALUE(id) AS id, ANY_VALUE(name) AS user_name,
       ANY_VALUE(age) AS user_age, ANY_VALUE(gender) AS gender
FROM maqbool_info
GROUP BY name
HAVING COUNT(*) > 1;   -- duplicates exist; any one row per name is fine — we only care THAT it repeats

ANY_VALUE says “engine's choice”. Legit when repetition itself is the finding; a smell when you secretly wanted MIN/MAX.

HAVING vs WHERE — the eternal interview question

WHEREHAVING

SQLthe canonical combo
SELECT gender, COUNT(*) AS people, AVG(age) AS avg_age
FROM maqbool_info
WHERE is_student = TRUE          -- 1st: throw away rows we don't care about
GROUP BY gender                  -- 2nd: bucket survivors
HAVING COUNT(*) > 10             -- 3rd: keep big buckets only
ORDER BY people DESC;            -- 4th: rank them
💡 Pro tip — filter early, filter cheap

Anything expressible in WHERE belongs in WHERE: rows discarded at step 2 never cost you grouping time. HAVING is only for aggregate conditions. The duplicate-hunt you'll run in Project 2 uses both: WHERE to scope, HAVING to judge the groups.

Grouping by several columns

SQL📓 Lecture 4
-- exact-duplicate detector: same name AND age AND gender more than once
SELECT name, age, gender, COUNT(*) AS copies
FROM maqbool_info
GROUP BY name, age, gender
HAVING COUNT(*) > 0;     -- > 1 to see only true duplicates

Multi-column keys bucket on the combination — here, each distinct (name, age, gender) triple gets its own row. Swap the key to find anything repeated: duplicate emails, duplicate order numbers, duplicate enrollments (Project 2 exploits this defensively with a UNIQUE constraint instead).

Subqueries — Queries Inside Queries

Sometimes the filter itself needs a query: “people whose age repeats”. Lecture 4 nested a GROUP BY inside a WHERE and it worked like a charm. This chapter formalizes the pattern — subqueries in WHERE, in SELECT, their NULL booby-trap, and when a JOIN is the better tool.

The shape: WHERE col IN (SELECT …)

SQL📓 Lecture 4
-- everyone whose age is shared by at least one other person
SELECT * FROM maqbool_info
WHERE age IN (
    SELECT age
    FROM maqbool_info
    GROUP BY age
    HAVING COUNT(age) > 1        -- inner: ages that appear 2+ times
)
ORDER BY age ASC;

Read it inside-out: the inner query computes the “wanted list”, the outer one filters against it. The inner query runs conceptually first (it has no dependency on outer rows — a non-correlated subquery).

🧠 Masterclass insight — decompose, then compose

The pro workflow for any nested query: run the inner query alone, look at its output (here: a column of repeated ages), then wrap it. If the inner result surprises you, the outer query was never your problem. Lecture 4 did exactly this dance — building the GROUP BY first, testing it, and only then embedding it in WHERE name IN (…) and its negated twin WHERE NOT name IN (…).

NOT IN — the NULL booby-trap

SQLthe classic production bug
-- ⚠️ if the inner query can return even ONE NULL,
-- NOT IN returns ZERO rows. Always. Silently.
SELECT * FROM maqbool_info
WHERE age NOT IN (SELECT age FROM maqbool_info GROUP BY age HAVING COUNT(*) > 1);

-- why: age NOT IN (21, NULL, 30) becomes
--      age <> 21 AND age <> NULL AND age <> 30
-- and age <> NULL is UNKNOWN for every row → nothing survives WHERE.

-- the safe forms:
SELECT * FROM maqbool_info
WHERE age NOT IN (SELECT age FROM maqbool_info GROUP BY age HAVING COUNT(*) > 1)
  AND age IS NOT NULL;                       -- guard the outer side

SELECT * FROM maqbool_info m
WHERE NOT EXISTS (SELECT 1 FROM maqbool_info x
                  WHERE x.age = m.age        -- EXISTS ignores NULLs entirely
                    AND x.id <> m.id);       -- (correlated form — see below)

Correlated subqueries & scalar subqueries

SQLpatterns
-- CORRELATED: inner query references the outer row → runs once per outer row.
-- People older than the average age of their own gender:
SELECT name, gender, age
FROM maqbool_info m
WHERE age > (SELECT AVG(age) FROM maqbool_info x
             WHERE x.gender = m.gender);

-- SCALAR: one value, usable anywhere an expression fits:
SELECT name, age,
       (SELECT MAX(age) FROM maqbool_info) AS oldest_in_table
FROM maqbool_info;

Relationships & Foreign Keys

Real data is connected: people place orders, live at addresses, enroll in courses. Lectures 5–7 built all three relationship shapes. This chapter names them, enforces them with foreign keys, and shows the one table trick that makes many-to-many possible.

The three shapes — all present in this dataset

Enforcing it: FOREIGN KEY

Lecture 6 didn't just join tables — it wired them so the database refuses orphan rows:

SQL📓 Lecture 6
-- the FK columns must exist, be NOT NULL, and match the parent's type:
ALTER TABLE orders  MODIFY user_id INT UNSIGNED NOT NULL;
ALTER TABLE address MODIFY user_id INT NOT NULL;

ALTER TABLE orders
  ADD CONSTRAINT fk_user_orders
  FOREIGN KEY (user_id) REFERENCES maqbool_info(id);

ALTER TABLE address
  ADD CONSTRAINT fk_users_address
  FOREIGN KEY (user_id) REFERENCES maqbool_info(id);

-- prove the wiring — ask the catalog:
SELECT TABLE_NAME, COLUMN_NAME, CONSTRAINT_NAME,
       REFERENCED_TABLE_NAME, REFERENCED_COLUMN_NAME
FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE
WHERE REFERENCED_TABLE_NAME IS NOT NULL
  AND TABLE_SCHEMA = 'maqbool';
🧠 Masterclass insight — referential integrity

A FK is a live promise: every child's user_id points at a real parent. Insert an order for user 9999 → rejected. Delete user 5 who has orders → rejected (default RESTRICT) — protecting you from orphaned data. The trade-off is real though: FK checks cost a little on writes, and legacy/bulk-loading systems sometimes skip FKs and enforce the rule in application code. Know which world you're in.

Many-to-many — the junction table

A student takes many courses; a course holds many students. No column can store that on either side — so Lecture 7 created a third table whose job is only to hold the pairs:

SQL📓 Lecture 7
CREATE TABLE student_courses (
    id            INT PRIMARY KEY AUTO_INCREMENT,
    student_id    INT NOT NULL,
    course_id     INT NOT NULL,
    enrollment_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_student FOREIGN KEY (student_id) REFERENCES students(id)
                           ON DELETE CASCADE,
    CONSTRAINT fk_course  FOREIGN KEY (course_id)  REFERENCES courses(id)
                           ON DELETE CASCADE,
    UNIQUE (student_id, course_id)     -- one enrollment per pair, ever
);

INSERT INTO student_courses (student_id, course_id) VALUES
(1, 1),  -- Arbaz   → MySQL
(1, 2),  -- Arbaz   → React
(1, 3),  -- Arbaz   → Node.js
(2, 1),  -- Maqbool → MySQL
(2, 3),  -- Maqbool → Node.js
(3, 2);  -- Zara    → React
🧠 Masterclass insight — two quiet geniuses in that DDL

ON DELETE CASCADE: delete a course and its enrollments vanish automatically — no orphans possible. (RESTRICT would refuse instead; choose per relationship.) UNIQUE(student_id, course_id): a composite constraint on the pair, not either column alone — Arbaz may take MySQL once, but Arbaz + MySQL twice is now impossible at the engine level. Composite keys are also the answer to “how do I prevent duplicate sign-ups/likes/follows” in any app.

Normalization in 60 seconds

  • 1NF — atomic values: no “phone1, phone2” columns, no comma-separated lists in one cell (why the junction table exists).
  • 2NF — non-key columns depend on the whole key (no “instructor name” stored inside student_courses).
  • 3NF — non-key columns depend on the key only (pincode city is not stored in address; it would drift when pincodes change — compute or join instead).

Your dataset already follows these — which is exactly why queries in Ch 12 need joins to reassemble it.

Normalization split the story across tables; joins put it back together. Lectures 5–7 practiced every join type against people, orders and addresses. Learn the two questions each join answers — “who matched?” and “who's missing?” — and 90% of join confusion evaporates.

The four join types at a glance

INNER JOIN
only rows that match in both tables
LEFT JOIN
all left rows; NULLs where no match
RIGHT JOIN
all right rows; NULLs where no match
CROSS JOIN
every combination — 127 × 500 rows

INNER JOIN — the workhorse

SQL📓 Lecture 5
SELECT m.id, m.name, m.age,
       o.order_number, o.status, o.total_amount
FROM maqbool_info AS m
INNER JOIN orders AS o ON o.user_id = m.id
ORDER BY m.name ASC
LIMIT 10 OFFSET 0;

-- same query, one filter on the joined table, cleaner with aliases:
SELECT m.name, o.status, o.total_amount
FROM maqbool_info m
INNER JOIN orders o ON o.user_id = m.id
WHERE o.status IN ('delivered', 'confirmed', 'pending')
  AND m.age NOT IN (21, 31, 44)
ORDER BY m.age ASC;
🧠 Masterclass insight — what ON really does

Conceptually, FROM a JOIN b ON … considers row-pairs where the condition holds (the storage engine uses indexes to skip most pairs — a nested-loop over an index, which is why FK columns should be indexed). People with no orders simply produce no qualifying pair, so INNER JOIN silently drops them. If “who never ordered?” matters — and it always does — you need LEFT JOIN (next).

LEFT JOIN — keeping the unmatched

SQL📓 Lecture 5
SELECT m.id, m.name, o.order_number, o.status, o.total_amount
FROM maqbool_info m
LEFT JOIN orders o ON o.user_id = m.id;

-- the anti-join: people with NO orders at all
SELECT m.id, m.name
FROM maqbool_info m
LEFT JOIN orders o ON o.user_id = m.id
WHERE o.user_id IS NULL;

For a person with no orders, LEFT JOIN still emits their row — with NULL in every orders column. That's the mechanism: left side preserved, missing right side becomes NULL. Filtering on o.some_col IS NULL therefore isolates exactly the no-match rows. This is the anti-join — the idiom behind “users with no purchases”, “students with no enrollment”, “products never ordered”.

⚠️ Watch out — WHERE can silently un-LEFT a LEFT JOIN

LEFT JOIN orders o … WHERE o.status = 'delivered' discards the NULL rows — the join might as well have been INNER. To filter the right table while keeping unmatched left rows, put the condition in the ON clause: LEFT JOIN orders o ON o.user_id = m.id AND o.status = 'delivered'. ON decides matching; WHERE decides surviving.

RIGHT JOIN, three-table chains, and FULL OUTER

SQL📓 Lectures 6 & 7
-- RIGHT = LEFT with the tables swapped; same engine work:
SELECT m.name, o.order_number, o.status
FROM maqbool_info m
RIGHT JOIN orders o ON m.id = o.user_id;

SELECT m.id, o.user_id FROM maqbool_info m
LEFT JOIN orders o ON o.user_id = m.id
WHERE m.id IS NOT NULL
UNION
SELECT m.id, o.user_id FROM maqbool_info m
RIGHT JOIN orders o ON m.id = o.user_id;

-- CROSS JOIN: every person × every product-sized table — rare on purpose.
SELECT COUNT(*) FROM maqbool_info CROSS JOIN orders;   -- 127 × 500 = 63,500

Transactions — COMMIT, ROLLBACK & ACID

Lecture 4 ran an UPDATE, saw the damage, and typed one word to undo it: ROLLBACK. That safety net is the transaction — the difference between “I hope my multi-step change works” and “it either all happens or none of it does”.

The demo you already ran

SQL📓 Lecture 4
START TRANSACTION;

UPDATE maqbool_info SET age = 23 WHERE name LIKE 'Arbaz%';
SELECT * FROM maqbool_info WHERE name LIKE 'Arbaz%';  -- changed… but only for ME

ROLLBACK;                                             -- ⏪ pretend none of it happened

SELECT * FROM maqbool_info WHERE name LIKE 'Arbaz%';  -- original ages restored

-- and the keep-it version:
START TRANSACTION;
UPDATE maqbool_info SET name = 'Arbaz khan' WHERE name = 'Arbaz';
COMMIT;                                               -- 🔒 now it's permanent

🧠 Masterclass insight — autocommit, the invisible default

MySQL commits every single statement automatically unless you're inside a transaction. That's why your one-off UPDATEs from earlier chapters were instantly permanent. START TRANSACTION suspends autocommit until COMMIT/ROLLBACK. Also crucial for the Ch 3 table: DDL statements (CREATE/ALTER/DROP/TRUNCATE) cause an implicit commit — you cannot roll back a TRUNCATE even inside a transaction, but you can roll back a DELETE.

💡 Pro tip — wrap risky UPDATE/DELETE in the ritual
START TRANSACTION;
UPDATE … ;  -- check the affected-rows count matches expectations!
SELECT … ;  -- eyeball the damage before committing
-- happy? COMMIT;  — horrified? ROLLBACK;

Long transactions block other writers and bloat undo logs — keep them seconds long, not hours. For checkpoints inside long jobs, use SAVEPOINT sp1; / ROLLBACK TO sp1;.

Views — Saved Queries as Virtual Tables

Lecture 7's best join ran over five lines and needed remembering every time. So the lectures saved it: CREATE VIEW GetALLCustomersData. A view is a named SELECT the database keeps on file — query it like a table, and the query runs fresh every time.

Create once, query forever

SQL📓 Lecture 7
CREATE VIEW GetALLCustomersData AS
SELECT m.id AS maqbool_id, m.name, m.gender, m.age,
       o.id AS orders_id, o.status, o.item_count, o.total_amount,
       ad.address, ad.pincode
FROM maqbool_info m
JOIN orders  o  ON m.id = o.user_id
JOIN address ad ON m.id = ad.user_id;

-- now the monster query is one line — with WHERE and ORDER BY on top:
SELECT * FROM GetALLCustomersData
WHERE pincode = 411001 AND status = 'confirmed';

SELECT * FROM GetALLCustomersData WHERE gender = 'male';

-- inspect your views:
SHOW FULL TABLES WHERE TABLE_TYPE = 'VIEW';
SHOW CREATE VIEW GetALLCustomersData;
SELECT TABLE_NAME AS view_name, VIEW_DEFINITION
FROM INFORMATION_SCHEMA.VIEWS
WHERE TABLE_SCHEMA = 'maqbool';
🧠 Masterclass insight — a view is a window, not a copy

No data is stored at CREATE time (it's “virtual”). Every SELECT on the view re-executes the underlying query against today's data — insert a new order and the view instantly shows it. Two consequences: views always reflect reality (great), but they are exactly as fast as their underlying query (a slow 5-table join stays slow behind a pretty name — indexes on base tables are what save you, Ch 17). MySQL has no materialized views; for heavy aggregates you'd summarize into a real table on a schedule.

Why views earn their place

  • Simplification — the triple join, its aliases, its quirks: written once. Consumers just SELECT.
  • A stable API — apps talk to GetALLCustomersData; when the schema underneath changes, you repair one view instead of hunting every query.
  • Security — grant access to a view exposing only name, pincode, never the base table with phones and ages.
  • Different lenses — Lecture 7 built GetCustomerWithOrderAndAddress with LEFT/RIGHT joins (keeping partially-matched people/addresses) and GetALLCustomersData with strict INNER joins (only fully-connected rows). Same data, two deliberate perspectives.

CASE & Conditionals — Tiers, Pivots, IFNULL

Raw rows rarely answer business questions — “which customers are Platinum?” does. CASE turns conditions into values, and dropped inside an aggregate it becomes a pivot machine. Lecture 7's tier labels and status dashboard are the perfect textbook.

CASE — if/else for values

SQL📓 Lecture 7 · slightly hardened
SELECT m.id AS users_id, o.status, o.total_amount,
    CASE
        WHEN o.total_amount <= 5000 THEN 'Silver'
        WHEN o.total_amount <= 9000 THEN 'GOLD'
        ELSE 'Platinum'
    END AS customer_tier
FROM orders o
JOIN maqbool_info m ON o.user_id = m.id
ORDER BY total_amount ASC;

Cases are checked top-down, first match wins — so order your WHENs from specific to general. That's also the bug-fix hiding in this listing: the lecture's original had WHEN total_amount >= 9001 THEN 'Platinum' with no ELSE, so a 9000.50 order fell through every branch and returned NULL. A trailing ELSE is cheap insurance — add it unless NULL is truly the answer you want.

CASE inside aggregates — the pivot

SQL📓 Lecture 7 · the status dashboard
-- four statuses, one row: the classic "wide report"
SELECT
    COUNT(CASE WHEN status = 'confirmed'  THEN 1 END) AS confirmed_count,
    COUNT(CASE WHEN status = 'delivered'  THEN 1 END) AS delivered_count,
    COUNT(CASE WHEN status = 'processing' THEN 1 END) AS processing_count,
    COUNT(CASE WHEN status = 'pending'    THEN 1 END) AS pending_count
FROM orders;

-- revenue split by status, same trick with SUM:
SELECT
    SUM(CASE WHEN status = 'delivered' THEN total_amount ELSE 0 END) AS delivered_revenue,
    SUM(CASE WHEN status = 'confirmed' THEN total_amount ELSE 0 END) AS confirmed_revenue
FROM orders;
🧠 Masterclass insight — why the NULL-then-COUNT dance works

Remember Ch 8: COUNT(expr) counts rows where expr is not NULL. CASE WHEN status='confirmed' THEN 1 END yields 1 for confirmed rows and NULL for everything else (no ELSE) — so each COUNT sees only its own status. For SUM the roles swap: ELSE 0 feeds zeros for non-matches. This conditional-aggregation pattern is the standard way to build cross-tabs (“rows = product, columns = month, cells = revenue”) before you ever meet the PIVOT-style fanciness other databases advertise.

NULLFirst aid: IFNULL & friends

SQL📓 Lecture 7
SELECT m.id, m.name, m.gender, m.age,
       IFNULL(m.phone_number, 'no phone') AS phone_number
FROM maqbool_info m;

-- the portable spelling (works in every database):
SELECT m.name, COALESCE(m.phone_number, m.gender, 'unknown') AS fallback_demo
FROM maqbool_info m;      -- returns the FIRST non-NULL among its arguments

Use these for display and defaults. For filtering, keep using IS NULL (Ch 6) — and never wrap the indexed column of a WHERE in a function when you can avoid it (Ch 16 explains why).

⚠️ Watch out

IFNULL(col, 'x') makes the output a string when col is numeric — fine for reports, wrong for math. And a CASE with mutually exclusive WHENs is a CHECK-constraint candidate: if tiers must exist for every amount, consider storing or validating the rule rather than trusting every future query to write its CASE correctly.

Indexes & EXPLAIN — Making Queries Fast

Everything so far was correctness; this chapter is speed. Lecture 6 built an index, re-ran EXPLAIN, and watched the execution plan change shape. Ten minutes of index literacy is worth more than any amount of micro-optimized SQL.

What an index is

Without an index, WHERE name LIKE 'Arbaz%' must read every row — a “full table scan”. An index is a sorted structure (a B-tree) of one column's values with pointers to their rows — the book's back-of-book index. Sorted data means lookups jump straight to the matches instead of reading everything. The bill: indexes consume disk and slow down writes slightly (every INSERT/UPDATE must maintain them). Index the columns you search, join and sort by — not every column “just in case”.

SQL📓 Lecture 6
EXPLAIN SELECT * FROM maqbool_info WHERE name LIKE 'Arbaz%';
-- type: ALL, rows: ~127  → full scan. Fix it:

CREATE INDEX idx_user_name ON maqbool_info(name);
CREATE INDEX idx_user_age  ON maqbool_info(age);

-- composite index — three columns, one structure:
CREATE INDEX multi_idx_user ON maqbool_info(gender, is_student, phone_number);

-- inspect & clean up:
SHOW INDEX FROM maqbool_info;
SELECT TABLE_NAME, INDEX_NAME, NON_UNIQUE, COLUMN_NAME
FROM INFORMATION_SCHEMA.STATISTICS
WHERE TABLE_SCHEMA = 'maqbool' AND INDEX_NAME != 'PRIMARY'
ORDER BY TABLE_NAME;

DROP INDEX idx_user_name ON maqbool_info;   -- (Lecture 6 dropped, recreated — indexes are cheap to rebuild)

🧠 Masterclass insight — the leftmost-prefix rule

A composite index is sorted like a phone book sorted by (surname, firstname): useful for surname lookups, surname+firstname lookups — but useless for firstname alone. So (gender, is_student, phone_number) serves filters on gender, gender+is_student, or all three — but a query filtering only phone_number ignores it entirely. Order composite columns by: equality filters first, range filters last, and put the most selective first. Lecture 6's experiment (gender LIKE 'male%' AND age = 21 against that index) demonstrated exactly the gap.

⚠️ Watch out — habits that blind indexes
  • Leading-wildcard LIKE '%arbaz%' can't seek — 'Arbaz%' can.
  • Wrapping the column in a function: WHERE YEAR(created_at) = 2026 → prefer a range: WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'.
  • Implicit type conversion (WHERE phone_number = 9876543210 against a VARCHAR) casts every row — quote it.
  • UNIQUE constraints create indexes automatically; the PK is an index too — user_id FKs deserve one for join speed.
💡 Pro tip — measure, change, re-measure

The workflow from Lecture 6 scales to production: EXPLAIN the slow query → form a hypothesis → create/drop an index → EXPLAIN again → keep only if rows/type improved. On tables with real data you can prefix with EXPLAIN ANALYZE to get actual timings. Project 3 walks the full loop.

WHERE row_condition            -- 2: filter rows
